# Design decisions

Log of the project's structural choices. Each decision has a stable identifier (`D1`, `D2`…).

**Process**: an open question is added under [To decide](#to-decide) with a `P<n>` identifier. Once decided, it moves to [Decided](#decided) with the next `D<n>` number. An identifier is never reused.

---

## Decided

### Sources

- **D1. Treize Mondial as the first source.** Its ["matchs du jour"](https://treizemondial.fr/matchs-du-jour-rugby-a-xiii/) page lists every rugby league match of the day on one page, with the final score added after the match. It has no API, so the page is parsed (HTML).
- **D2. One adapter per source.** Each source has its own adapter that returns the same normalised result (competition, date, teams, score). The rest of the pipeline never knows where a score comes from, so adding a source only adds an adapter.
- **D3. French amateur football (FFF) left out.** Its JSON API works from a browser but answers `403` to requests from AWS.
- **D27. Reading the Treize Mondial page.** The page is hand-edited HTML with no meaningful classes, so it is parsed by the shape of its table rows (day header, competition, two rows per match) with [node-html-parser](https://github.com/taoqf/node-html-parser), lighter than cheerio and sturdier than regular expressions. An unknown row shape or a second day on the same page fails loudly, since it means the layout changed; an odd cell value (no kick-off time, no score) only leaves that field empty. A match counts as finished only when marked `✔` (text or emoji form) with both final scores: a half-time score (`MT`) is never sent. Only the final score is read, as the half-time scores on the page do not always add up. The page shows no year, so the date comes from the request and the page header only has to match its day and month. When the main page has already moved to the next day (a late match checked after midnight), the adapter also reads `/2`, which held the previous day when checked on 2026-11-01. The date of every page read is checked, so if the site orders its pages differently the match is reported as not found, never with another day's score. Requests name the bot in their User-Agent rather than posing as a browser.

### Scheduling

- **D4. A morning planner instead of hourly polling.** One run each morning reads the day's kick-off times and creates one **one-time schedule** per match, about 2 hours after kick-off. Compared with polling every hour: far fewer runs, the source website is read only when a result is expected, and nothing runs on days without matches. Trade-off: a match added to the page after the planner has run is not scheduled.
- **D5. Reschedule when the score is late.** If the score is not published when the schedule fires, `fetch-results` creates a new schedule one hour later instead of failing. _Replaced by D35: the delay grows from one attempt to the next._
- **D31. The planner runs at 10:00, Paris time.** A recurring EventBridge Scheduler schedule (`cron(0 10 * * ? *)`, time zone `Europe/Paris`, so daylight saving is handled by AWS) runs `planner`. By 10:00 the page of the day has had time to fill in, which narrows the trade-off of D4 and the missing kick-off times of D34. A match whose check is already due by then (a night match abroad) is checked a minute after the planner runs. The planner reads the day through the adapter (`listDayMatches`), which fails if the main page is not for the Paris date: the run fails loudly instead of scheduling another day's matches. A match whose schedule cannot be created does not stop the others: each failure is logged with its match id, the run fails at the end, and Lambda's retry finds the other matches already scheduled.
- **D32. One-time match checks.** Each check is a one-time schedule in the `final-whistle-match-checks` group, set with an `at()` expression in Paris wall-clock time and the `Europe/Paris` time zone, never in the past (at least a minute ahead). It invokes `fetch-results` with the match check (D28) and deletes itself once it has run. `planner` creates the first attempt of each match, `fetch-results` the next ones (D35). Schedule names only allow letters, digits, `-`, `_` and `.`, so the name is `match-`, 32 hex characters of the SHA-256 of the match id, then the attempt (`match-…-2`): the same on every run, so running the planner again creates nothing new while the checks are pending (`ConflictException` counts as already scheduled). A check that has already run has deleted itself, so it is created again and the match checked once more; a score already sent is then dropped by `notify` (D8). Scheduler invokes `fetch-results` with its own role, which may do nothing else; `planner` and `fetch-results` may only create schedules in that group and pass that role to Scheduler. Both Scheduler roles (match checks and the morning schedule) only trust schedules of this account (`aws:SourceAccount`). Two cdk-nag `IAM5` wildcard findings are acknowledged on their resources (D22): schedule names are computed at run time (on each Lambda that creates schedules), and the CDK Lambda target also grants the planner's versions and aliases. The morning schedule stays in the default group, out of reach of the planner's rights. Scheduler is in the Always Free quota (D17).
- **D33. Quiet hours: no check from 23:00 to 08:00, Paris time.** A check due in that window is moved to 08:00, so no score is published, and no notification sent, at night. The rule lives where checks are scheduled, so `notify` stays unaware of it. Limit: a `notify` invocation that fails just before 23:00 is retried by Lambda a few minutes later, so a message can arrive shortly after 23:00.
- **D34. A missing kick-off time is checked at 17:00** (was P2). When the page gives no kick-off time, the first check is at 17:00: 15:00, the most common kick-off on the saved pages, plus 2 hours. The planner logs a warning, so the frequency of the case is measured. It was absent from the 29 matches of the saved pages.
- **D35. Growing delays between attempts.** When a check finds no score, `fetch-results` schedules the next attempt itself, after 1 h, 1 h, 1 h, 2 h, 4 h, then 8 h, each moved out of the quiet hours (D33). From a first check at 17:00, the attempts run at 17:00, 18:00, 19:00, 20:00, 22:00, 08:00 and 16:00 the next day: the evening, when most scores are published, is checked every hour, and a score published late is still caught the next day, with 7 attempts rather than one an hour. These delays are a guess, not a measured figure: the logs (attempt of each published score, matches given up) will show whether to change them, in one constant. The next attempt is created before the run ends, so a run retried by Lambda finds it already scheduled. `fetch-results` reads its own ARN from the Lambda context rather than its environment: the stack cannot give a function its own ARN, as the invoke role already depends on the function. That ARN is the one Scheduler invoked: once `fetch-results` runs behind the `prod` alias (D15), it ends with `:prod`, so the invoke role must then allow the alias, or the next attempts are denied.
- **D36. A match is given up after 7 attempts** (was P3). After the 7th check without a score, about 23 hours after a first check at 17:00, the match is logged as `match given up` (warning) and not checked again: by then it was most likely postponed or abandoned. A match not found on the page is retried the same way as one not finished, as the page is edited by hand and may be fixed later; it keeps its warning. Each attempt writes a single log line, with the attempt number and the time of the next one.

### Events and delivery guarantees

- **D6. An event bus between detection and notification.** `fetch-results` publishes a `MatchFinished` event instead of calling `notify` directly. The producer does not know its consumers: a new one (history, website rebuild) is a new rule on the bus, with no change to the producer (fan-out). Each consumer handles its own failures. Cost: one more hop, and custom events are billed ($1 per million, a fraction of a cent here).
- **D7. At-least-once delivery: send, then record.** `notify` checks DynamoDB, sends to Telegram, then records the score. A crash between sending and recording means a duplicate message, never a lost score. A rare duplicate is accepted.
- **D8. Idempotence key**: the page date and both teams, e.g. `2026-10-30|Angleterre|Papouasie-Nouvelle-Guinée`. Team names are kept exactly as published.
- **D9. Failed events go to a DLQ.** After Lambda's retries, a failing event lands in an SQS dead-letter queue, watched by an alarm, instead of being lost silently. _Detailed in D37._
- **D28. The `MatchFinished` contract.** `fetch-results` takes the match check `{ date, homeTeam, awayTeam, attempt }` (the key of D8 and the attempt number of D35, from 1) as input and validates it first: a malformed check fails at once instead of being looked up and rescheduled. A finished match is published on the `final-whistle` bus as `MatchFinished` (source `final-whistle.fetch-results`); its detail is the normalised result plus its match id, so consumers never rebuild the key. The bus is created with its producer and each consumer adds its own rule (D6). Source, type and detail are defined once in `src/events`, for the producer and the rules. PutEvents reports a rejected entry without throwing, so a rejection is turned into an error: the invocation fails and is retried instead of losing the score.
- **D30. `notify`: check, send, remember.** `notify` is subscribed to `MatchFinished` by its own rule and validates the event detail first, against the contract in `src/events` (D28). It then follows D7:
  - **Check**: a strongly consistent read of the match id in the `SentMatches` table, so a score recorded a moment ago is always seen.
  - **Send**: a plain-text message in French, so that no team name is read as Telegram formatting: `Score final · SUPER XIII`, then `Carcassonne 22 – 18 Lézignan`. The request is cut after 10 s.
  - **Remember**: a conditional write of the match id and the send time. If the match is already there, another invocation sent the same score at the same moment: the duplicate is accepted (D7) and logged as `duplicate sent`, so its frequency is measured rather than guessed. It is not prevented: reserving a concurrency of 1 for `notify` would serialise invocations, but the account's limit of 10 concurrent executions leaves nothing to reserve, and claiming the match before sending would break the order of D7, losing the score if `notify` crashed in between. If the warnings show duplicates are not rare, the next step is a higher limit and a reserved concurrency of 1.
  - **Table**: provisioned at 1 read and 1 write unit (D10), kept if the stack is deleted and protected against deletion. Point-in-time recovery is not enabled (cdk-nag `DDB3` acknowledged on the table): it is billed (D17), and losing the table costs at worst one score sent twice, never a lost score.
  - **Telegram parameters**: `/final-whistle/telegram/bot-token` (SecureString) and `/final-whistle/telegram/chat-id` (String), created by hand before the first deployment, since CloudFormation cannot create a SecureString. They are read together in one `GetParameters` call on the first send of each Lambda instance and kept in memory; SSM reports a missing parameter without throwing, so it is turned into an error naming it. They are not resolved at deployment, because CloudFormation would read them with the CDK deploy role, which may only read the bootstrap version. The role may only call `ssm:GetParameters` on these two parameters, with no KMS permission: the AWS-managed key lets SSM decrypt for the account's roles.
  - **No token in the logs**: the bot token is part of the Telegram URL, so a failed request is reported by the match, the error name and its system code only (e.g. `TypeError ECONNRESET`); the original error, which may quote the URL, is never kept. A rejection keeps the HTTP status and Telegram's `description`.
- **D37. One failure queue for every asynchronous step** (details D9). Nothing in the pipeline waits for an answer, so a failure is never seen by a caller: each step that can drop an event sends it to the same SQS queue instead.
  - **Lambdas**: `planner`, `fetch-results` and `notify` send an invocation that still fails after Lambda's 2 retries to the queue as an on-failure destination, rather than a plain dead-letter queue: the message holds the original event, the error and the function, so one queue serves the three Lambdas and a failure is understood without searching the logs. The destination is set on `$LATEST`, the version invoked today; once the schedules and the rule invoke the `prod` alias (D15), it has to move to the alias.
  - **Launchers**: the morning schedule, the match check schedules and the `MatchFinished` rule send what they cannot deliver to their Lambda (a permission removed or a function renamed by a broken deployment) to the same queue, after their own retries (up to 24 h). Each one may only send to that queue: Scheduler through its invoke role, EventBridge through the queue policy, limited to the rule. Such a message holds the original event, with the reason in its attributes.
  - **Queue**: 14 days of retention, the longest SQS allows, encryption by SQS (free) and HTTPS only. It has no dead-letter queue of its own (cdk-nag `SQS3` acknowledged): it is the last stop, watched by an alarm (D39). A failure is replayed by hand.
- **D38. Alerts by email through SNS.** The alarms publish on the `final-whistle-alerts` SNS topic, which sends an email. Telegram was the first choice, but an alert must not depend on what it watches: when Telegram or the bot token fails, `notify` fails, and an alert sent through Telegram would fail with it. Email needs no code (no Lambda to relay the alert) and stays free (1,000 emails a month). The subscription is created by hand once the topic exists, so the address never enters the public repository or the `cdk diff` of a pull request. The topic accepts HTTPS only and is not encrypted at rest (cdk-nag `SNS2` acknowledged): CloudWatch alarms cannot publish on a topic encrypted with the AWS-managed key, a customer-managed key is billed (D17), and the topic only carries alarm states.
- **D39. Alarms on failures of the system, not on missing scores.** A postponed match is not a problem; a pipeline that silently stops working is. Three alarms, each notifying the topic when it goes to ALARM:
  - **Message sent to the failure queue**: any message arriving in the queue of D37, which covers every error the Lambdas rethrow (D29) and every event a launcher could not deliver. The alarm counts arrivals (`NumberOfMessagesSent` over 5 minutes), not the messages waiting: a message left in the queue would keep an alarm on its level in ALARM for up to 14 days and hide every later failure. Each new failure raises a new alert, and the alarm returns to OK on its own.
  - **Match not found**: a match given up while still not found on the page (`match given up` with `status: "not-found"`, counted by a log metric filter). `planner` found it that morning, so `fetch-results` failing to find it for 7 attempts points to a lookup problem (a team name edited on the page, a page moved). A match given up as `not-finished` raises nothing. Assumption, not observed yet (no saved page has a postponed or cancelled match): a postponed match stays on the page without a score, so it ends as `not-finished`. If Treize Mondial removes its row instead, this alarm fires on a postponement, and it is revisited then.
  - **Planner not run**: no `planner` invocation for 26 hours (hourly invocation counts, an hour without data counting as none). The planner runs every day, even without a match, every 24 h (25 h when the clocks go back), so silence means its schedule no longer fires, which leaves no error to catch.
  - **Cost**: 3 of the 10 free alarms and 1 of the 10 free custom metrics.

### Data and secrets

- **D10. DynamoDB in provisioned mode (1 read / 1 write unit).** The Always Free quota covers provisioned capacity, not on-demand. The load is a few writes per match day.
- **D11. Telegram as the notification channel.** Free, a real push notification on the phone, and a simple HTTP API.
- **D12. Secrets in SSM Parameter Store** (SecureString, AWS-managed key), never in the code, the repo or the logs. Preferred to Secrets Manager, which is billed per secret. The token is read once per Lambda instance and kept in memory (D30).

### Infrastructure and delivery

- **D13. AWS CDK in TypeScript** rather than Terraform: the same language as the Lambdas, security rules checked with cdk-nag, and deployments through CloudFormation, which rolls back a failed change.
- **D14. Deployment from GitHub Actions through OIDC.** GitHub assumes a short-lived AWS role: no access key is stored anywhere.
- **D15. Safe deployment: versions, `prod` alias, smoke test, automatic rollback.** Each deployment publishes new Lambda versions; the alias moves only if the smoke test passes.
- **D16. Every change goes through a pull request.** `main` is protected, squash merge only, all required checks must pass.
- **D22. cdk-nag blocks the pull request.** Its AWS Solutions rules run during `cdk synth`, so a violation fails the check and blocks the merge. When a rule does not fit (often because it asks for a paid option, see D17), it is acknowledged on that resource with a written reason, never disabled for the whole app.
- **D23. GitHub OIDC trust lives in its own stack, deployed by hand.** CI cannot create the role it signs in with, so `FinalWhistleGithubOidc` (the provider and the two roles) is deployed manually with `cdk deploy`. A change to it shows up in the pull request diff and is deployed by hand again. Automated deployments target the `FinalWhistle` stack only, never this one, so a pipeline can never widen its own trust.
- **D24. Two GitHub roles: pull requests read, `main` deploys.** The pull request role trusts only `repo:TomSoulage@76871522/final-whistle@1440617490:pull_request` (GitHub's immutable subject format, with the owner and repository ids) and can only assume the read-only CDK lookup role, used by `cdk diff --method=template`. The deploy role trusts only `…:environment:production`, which only `main` can use (D26). It was created with the pull request role, before the pipeline existed; moving its trust to the `production` environment (D26) took one more manual deployment. Through the CDK deploy role, it reaches the bootstrap CloudFormation execution role, which still has `AdministratorAccess` until it is restricted ([#13](https://github.com/TomSoulage/final-whistle/issues/13)). Fork and Dependabot pull requests get no OIDC token, so the diff job is skipped for them. The diff goes to the job summary rather than a PR comment, so CI needs no write access to pull requests.
- **D25. A standalone AWS account, not an AWS "project" account.** Project accounts (the new AWS sign-up, e.g. with GitHub) carry AWS-managed service control policies that deny `iam:*Provider*` on both the Free and the Paid plan, which rules out OIDC (D14). A standalone account has no such policy. Daily access goes through an IAM user with MFA and `aws login`; the root user has MFA; no access keys exist.
- **D26. Continuous deployment through the GitHub `production` environment.** Every push to `main` runs `cdk deploy` on the `FinalWhistle` stack, with no manual approval: the safety net is the pull request checks before the merge and, once the Lambdas exist, the smoke test and alias rollback after it (D15). The deploy job is bound to the `production` environment, which gives a deployment history in GitHub and a branch policy allowing `main` only, with no administrator bypass. Binding a job to an environment changes its OIDC subject to `…:environment:production`, so the deploy role trusts that subject (D24): the branch restriction is enforced by the environment, not by AWS. Deployments run one at a time and are never cancelled midway, so CloudFormation is never interrupted. The pull request checks are not run again before deploying; `cdk deploy` synthesizes again with cdk-nag anyway. Jobs that can request an AWS token install dependencies with `npm ci --ignore-scripts`, so a compromised package cannot run code while that token is within reach.

### Cost and repository

- **D17. €0 to run.** Every service stays within the AWS Always Free quotas. The cost of any new resource is checked before adding it.
- **D18. Public repository from the first commit.** It makes the free security features available (CodeQL, secret scanning with push protection). Consequence: no secret may ever be committed, which Gitleaks and push protection enforce.
- **D19. English** for code, docs, commits and pull requests. Team and competition names stay as published (French).

### Tooling and dependencies

- **D20. Toolchain: npm, TypeScript 6.0, ESLint, Vitest, commitlint, tsx.** tsx runs the CDK app, as `cdk init` sets it up. Node 24 (`.nvmrc`). TypeScript stays on 6.0 because typescript-eslint does not support 7.x yet. ESLint enforces the measurable code rules of `CLAUDE.md`. Commitlint checks the PR title, since it becomes the squash commit, as well as each commit. Actions are restricted to GitHub-owned ones plus an explicit allowlist in the repository settings (currently `gitleaks/gitleaks-action` and `aws-actions/configure-aws-credentials`), and must be pinned to a full commit SHA; Dependabot keeps them up to date. A new third-party action needs an allowlist entry first.
- **D21. Dependabot sorts updates by risk.** Minor and patch updates are grouped into one weekly pull request, which should stay green. Each major update gets its own pull request, so a breaking one never blocks the safe ones. New versions are proposed only after a 7-day cooldown, to avoid compromised releases that get pulled within days. Two majors are ignored because their version is a decision, not a default: `typescript` (revisit when typescript-eslint supports 7.x) and `@types/node` (revisit when the Lambda Node.js runtime changes).
- **D29. Structured logs without a library.** An in-house JSON logger (one object per line on stdout) rather than Powertools: a few lines, no dependency. The context (Lambda name, match id) is on every line and cannot be overwritten by a field. A failure is logged with its chain of causes, then rethrown so that Lambda retries it. Each Lambda has its own log group, created by the stack with a one-month retention.
